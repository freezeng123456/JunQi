## 无法从现有历史恢复的内容

- 训练 checkpoint 二进制（旧记录引用的 `ckpt_000300.pt` 约 211 MB）没有在本地 checkout、GitHub 对象或新服务器上找到，因此不能声称已经恢复模型参数。
- 旧服务器 `2c238c9` 的完整 Git 对象不在当前 GitHub 仓库中；本分支恢复了仍有源码/产物依据的行为，不伪造缺失 commit 的逐行 patch。
- 旧服务器释放前启动的后续 self-play 长跑 checkpoint 也没有可用副本。

旧训练记录仍保留在复盘元数据和报告中，可用于重新建立实验：运行标识为 `h20_long_300_256x1024_20260815`，原记录使用 CUDA、greedy policy、random opponent、Top-K=16 和 belief 记录。

从旧服务器长跑日志中还能确认：rollout 300 的随机对手评估约为胜 `0.945`、负 `0.047`、和 `0.008`；之后启动的 self-play 延续任务及其新 checkpoint 随旧服务器释放一并不可取回。这些数字只能作为历史实验记录，不能替代 checkpoint 的重新验证。

旧长跑中还能确认的训练快照如下；这是根据启动参数和日志整理的复现实验线索，不是从缺失的 checkpoint 反推出的配置文件：

| 项目 | 已知值 |
|---|---|
| 并行环境 / 每环境步数 | `256 / 1024` |
| rollout 总数 | `300` |
| GPU rollout | 开启 |
| PPO dtype | `bfloat16` |
| random opponent | 开启 |
| belief / ARR | `belief_enabled=false` / `arr_enabled=true` |
| reward shaping / storage | 开启 / `full_obs` |
| eval/save 间隔 | `20` |
| seed | `101` |
| sparse action head | 关闭 |

H20 上曾尝试 `torch.compile`；self-play 路径出现 cuBLASLt divide 错误后，稳定运行采用了 `torch_compile=false` 并配合 `CUDA_LAUNCH_BLOCKING=1`。这条 workaround 应作为重新训练时的默认安全配置，而不是声称旧长跑已经使用了它的最终版本。

本恢复分支没有修改 `junqi_rl/training/ppo.py`：当前 GitHub 基线已有自己的 action-level KL 近似，而缺失的 `2c238c9` 完整对象无法逐行核对。这样处理是为了保留可审计的历史恢复边界；下一轮 KL 诊断应在新分支上单独提交、单独跑 smoke 和长跑。

## 校验约定

恢复完成后至少执行：

1. `git diff --check`；
2. `pytest tests/test_replay_web_data.py`；
3. `make -C legacy_gui PROFILE=release`（在具备 GTK3 开发依赖的环境）；
4. 对现代复盘执行 `TrajectoryWithPolicy.validate()`，并核对原生 `.jql` 与元数据校验和。

checkpoint 缺失不影响复盘文件和客户端恢复，但重新训练必须从 GitHub 基线或新的 checkpoint 开始，并单独记录新的 commit、配置和指标。
